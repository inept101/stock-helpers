# Kite operations

## Session and data

- Kite Connect Personal provides account reads and order management. Live quotes, market depth, streaming, and historical candles require a market-data entitlement or a separately verified provider. The holdings response includes a last-traded price for positions it reports. Treat that value as a reference price and distinguish it from a timestamped bid or ask. [Kite plan comparison](https://support.zerodha.com/category/trading-and-markets/general-kite/kite-api/articles/what-are-the-charges-for-kite-apis)
- The app's API key and the current session access token authenticate requests using the Kite Connect format. Keep both the API secret and access token local. Exchange each browser request token once and reuse the resulting session token. When a refresh fails, distinguish an expired session from a permissions or connectivity error. [Kite authentication](https://kite.trade/docs/connect/v3/user/)
- For holdings after a sale, sync again after verifying fills. The active portfolio uses the current holdings quantity and available pending quantities, while the broker may return sold-out rows with zero units. After a demerger, cross-check the lot breakdown and realised P&L in Console before using the API average as a tax cost basis. [Kite holdings endpoint](https://kite.trade/docs/connect/v3/portfolio/) · [Zerodha P&L report](https://support.zerodha.com/category/console/reports/profit-and-loss-report/articles/where-can-i-get-my-profit-and-loss-reports-from)

## Explicitly requested live orders

1. Resolve the authorised order scope. Check side, instrument and exchange, quantity, product type, and pricing instruction. A research brief is a proposal. Use the user's explicit trade instruction before placing an order, and resolve material ambiguity such as an optional trim the user has not selected.
2. Read the current order book and relevant fills before sending an order. Check sellable quantity for exits and available funds and charges for buys. Account for pending or partially filled orders so a retry cannot duplicate an order. Check exchange hours and use a fresh, timestamped price for the chosen venue. Use the available bid or ask where possible. If using a last-traded price to set a limit, state that assumption and the possibility that the limit remains unfilled.
3. For an API order, verify that the actual outgoing public IP matches a static IP on the Kite Connect developer whitelist. Use the corresponding IP family if the machine has both IPv4 and IPv6. For a delivery sell, use CNC and verify CDSL authorisation for the shares unless DDPI or POA covers the sale. CDSL TPIN and OTP authorisation is completed by the user in Kite and generally applies for the trading day. A same-day MIS position is an intraday trade and must be closed by the applicable cutoff. [Static IP setup](https://support.zerodha.com/category/trading-and-markets/general-kite/kite-api/articles/static-ip) · [CDSL authorisation](https://support.zerodha.com/category/trading-and-markets/trading-faqs/general/articles/tpin-preauthorisation) · [Kite product types](https://support.zerodha.com/category/trading-and-markets/charts-and-orders/order/articles/what-does-cnc-mis-and-nrml-mean)
4. The local CLI has no order submission command. Use the documented Kite Connect `POST /orders/regular` endpoint if sending an authorised order programmatically. Use a descriptive order tag to make reconciliation easier. Keep the token out of command output and avoid passing it in visible command-line arguments. After submitting, read back the order status and executed fills. If the response times out or is ambiguous, reconcile via the order book and tag before any retry. Report the order ID, limit, filled quantity, execution price, and open, filled or rejected status. An order ID records submission and the trade record confirms execution. [Kite Orders API](https://kite.trade/docs/connect/v3/orders/)
